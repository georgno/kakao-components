# catalog Specification

## Purpose

A short guide (CATALOG.md) that lets a project use the library from a few thousand tokens of context: how to load it, the names every component shares, which look-alike to pick and one line per component, generated so it can't drift from the components.

## Requirements

### Requirement: Consumer catalog
`CATALOG.md` SHALL give a project that uses the library, in about 3k tokens: the minimal page head (the loader: kakao.css and kakao.js; and the single-file head: tokens, font, themes, component-api, the theme switch loaded early so the theme doesn't flash), vendoring with `tools/vendor.js`, the light-DOM components that work without JS, a shared contract written once (label, size, tone, list-data, hidden, event naming, escaping JSON in attributes with one-line helpers for Python, PHP and JS), a "which one?" table for look-alike components, and one line per component.

#### Scenario: Picking between look-alikes
- **WHEN** an agent wonders whether to use kakao-alert or kakao-toast
- **THEN** the "which one?" table answers it in one row

#### Scenario: Shortest head
- **WHEN** an agent starts a page
- **THEN** the page head section shows the two-line loader head first

### Requirement: Generated component lines
Each component line SHALL be generated by `node tools/catalog.js` from custom-elements.json: the tag (and the other tags of its file), what it is for (`summary`), when not to use it and what to use instead (`kakao.notFor`), light DOM with its CSS file, and the components to load first. Shadow-DOM components without dependencies are unmarked, as the list's intro says. Only the part between the `catalog:start` and `catalog:end` markers is generated; the rest is written by hand.

#### Scenario: Toast
- **WHEN** the catalog lists kakao-toast
- **THEN** its line says light DOM and to load kakao-stack and kakao-alert first

### Requirement: Catalog kept current
`node tools/catalog.js --check` SHALL exit with code 1 when the generated part differs from custom-elements.json, or when the file names a `kakao-<name>` that is neither a tag nor an event of the manifest. The pre-commit hook and the deploy SHALL run it, and the deploy SHALL publish CATALOG.md.

#### Scenario: Component renamed
- **WHEN** a component is renamed and the hand-written table still names the old tag
- **THEN** `--check` fails and names it
