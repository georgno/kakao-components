# Design

## Decisions

- **Light DOM, with `table.css`.** The table, its rows and its cells stay in the page. The reasons, in order of weight:
  1. *Server-rendered tables.* A Yii2 GridView arrives as a finished `<table>` with links, buttons and `data-method` / `data-confirm` attributes that page scripts handle by delegation at the document. Slots only take direct children of the host, so cells of a slotted table cannot be laid out by a shadow table; copying or moving cell content into a shadow root would retarget its events and break those scripts. Enhancing the table where it is keeps all of that working.
  2. *Before the script.* `kakao-table table { … }` styles the server's table as soon as the stylesheet is in, so the page neither jumps nor shows an unstyled table while the script loads.
  3. *Forms.* The row checkboxes are native inputs in the page, so `selection-name` is all it takes to submit the selection (`selection[]`, as Yii2's CheckboxColumn names it).
  4. *Grid view.* Filters and action buttons are other components placed in heading and body cells; in the light DOM they are simply there, with no slot per cell.
  The price is the usual one for light DOM: page CSS reaches in, so every rule is scoped under `kakao-table` and the classes it adds are prefixed `kakao-table-`.
- **One path for both sources.** `list-data` (or `columns` / `rows`) is first drawn as a plain native table (`<th data-key data-type …>`, `<tr data-key>`); from there on the same code enhances it that enhances a server table: roles, `scope`, sort controls, `data-label` on cells, the selection column, empty-cell placeholders. So the two sources cannot drift apart, and what is documented for server markup (the `data-*` attributes) is exactly what the component writes itself. `list-data` wins over a child table.
- **Column model.** A column is `{ key, label, type, align, sortable, width, hideLabel }` plus, from script, `render(value, row, column)`. `type` looks up `KakaoTable.types[type]` (`align`, `compare`, `format`); `text` and `number` are built in. Rows are objects by key or arrays in column order; the row id is `row[row-key]` (default `id`), `data-key` / `data-id` on a server row, else the position.
- **Sort state the Yii2 way.** One attribute, `sort="name"` or `sort="-name"`, the value Yii2 puts in `?sort=`. A heading cycles ascending, descending, unsorted (rows as written). `sort-change` is cancelable and carries the new value, so server mode is "listen, load, set `rows`". In the browser, rows are re-ordered inside their own `<tbody>`, empty cells last, by `data-sort-value`, the raw `list-data` value, or the cell text. A heading whose only content is a link is treated as the server's sorter: it becomes the sort control as it is (icon, `aria-sort` from the link's `asc` / `desc` class) and stays a link.
- **Selection is ids.** The component keeps a set of row ids; checkboxes, `data-selected` on the row and both "select all" boxes (heading row and wrapped tools) are drawn from it, so it survives sorting and re-rendering. Ids of rows that are gone are dropped. User changes and the two methods fire `selection-change`; setting `selected` is silent.
- **Wrapped form by the element's width.** As `kakao-description-list` does: a ResizeObserver compares the element's width with `--kakao-table-stack-below` (36rem, measured through a hidden probe) and sets `data-stacked`. CSS then turns rows into blocks; each cell shows its column heading from `data-label` through `::before`, floated into the cell's padding so any cell content (text, links, buttons) wraps beside it. The heading row is `display: none`, so sticky does not apply. Because the rule says sort stays usable, a tools line above the blocks carries "Select all" and a native "Sort by" select (one option per column and direction; a link heading is one option that follows the link). Table, row and cell roles are set explicitly so the semantics survive `display: block`.
- **Scrolling is the opt-in `scroll`.** The frame gets `overflow: auto`, the table a minimum width of the wrap threshold, and the frame the edge-fade mask on each side with more to scroll (`--kakao-table-scroll-fade`, default `--kakao-scroll-fade`). A frame that overflows is focusable and a named region, so it scrolls from the keyboard. `--kakao-table-max-height` also lets it scroll down; the sticky header then sticks to the frame. Without `scroll` the frame never becomes a scroll container (a bordered frame uses `overflow: clip`), so the sticky header sticks to the page at `--kakao-table-sticky-top`.
- **Optional components.** Empty state and loading rows use `kakao-empty-state` and `kakao-skeleton` when they are defined, and are redrawn when they get defined later; otherwise a plain text and a pulsing bar. The table sets attributes on them and nothing else. A pager is not wired in at all: the demo shows a `kakao-pagination` below the table, joined by a few lines of page script.
- **Following the page.** A MutationObserver redraws when the table's structure changes (rows, cells, the table itself), not when cell content does, so components that rewrite their own children in a cell (kakao-button) cause no work, and pjax replacing the rows is picked up. The component's own writes are made with the observer off.
- **`dense`, not `size="sm"`.** The request names the three forms striped, dense and bordered; siblings use `size="sm"` for their dense form. Left as `dense` for the user to decide.

## Extension points for Grid view

Grid view is expected to compose a `kakao-table` (render one inside itself, or wrap a server table with it) rather than subclass it, because `table.css` is scoped to the `kakao-table` tag. What it builds on:

- **Columns.** `columns` accepts extra keys untouched and returns them, so a grid can keep `filter: { type: "search" | "select", options }` on a column. `render(value, row, column)` draws action cells; `hideLabel` is the action column's heading (read out, not shown, no label in the wrapped block). `KakaoTable.types` takes new types (`date`, `money`, `actions`) with `align`, `compare` and `format`.
- **Heading rows.** Only the first row of `<thead>` is read as headings and enhanced. Further rows there are left alone and are found again after every render: the filter row. `th` cells keep `data-key`, so a filter cell can be matched to its column.
- **Wrapped form.** `<thead>` is hidden when wrapped. `.kakao-table-tools` (the line above the blocks) is a stable container: the table only replaces its own `.kakao-table-tool` children, so a grid can append its filters there (or a "Filters" button) and they stay. `stacked` and the `data-stacked` attribute say which form is shown.
- **Sort.** The icon per heading, `aria-sort`, `sort` and `sort-change` are done here; a grid adds nothing for sorting. With `sort-mode="server"` it reloads on `sort-change`.
- **Lifecycle.** `table-render` fires on the element after every read or redraw, the moment to (re)place filters or decorate cells. `refresh()` re-reads after outside changes. `loading` and the empty state cover the reload.
- **Selection and paging.** `selected`, `selection-change` and `selection-name` are the bulk-action hooks; a `kakao-pagination` goes below, as in the demo.
- **Class.** `window.KakaoTable` is exported for `instanceof` checks and the static `texts` / `types`.

## Out of scope

- Filters, the action column's buttons, column resizing, reordering and hiding, row expansion, virtual scrolling, inline editing.
- Paging and loading data.
- `colspan` / `rowspan` in the body, a `<tfoot>` in the wrapped form (it stays a plain row), single-row selection, shift-click ranges.
- A server table's own checkbox column: `selectable` adds the component's.
