# Design

## Decisions

- **Light DOM, composing a table.** `table.css` is scoped to `kakao-table` and a server's GridView arrives as page markup, so the grid cannot draw its table in a shadow root. It renders, in itself: a bar (summary, clear filters), a `kakao-table` and a `kakao-pagination`. A `kakao-table` or `kakao-pagination` written inside it is used as it is (server markup). Every rule in `grid-view.css` is scoped under `kakao-grid-view`, its classes are prefixed `kakao-grid-view-`.
- **Who sorts, filters and pages.** Client mode (the default, rows from `list-data` / `rows`): the grid keeps all rows, filters them, sorts them with `KakaoTable.types[type].compare` (the table's registry, empty values last), cuts the page and hands only that to the table. The table is set to `sort-mode="server"`, so its headings, icons, `aria-sort` and "Sort by" stay its own, and the grid answers `sort-change` after it (microtask, so a cancelled event changes nothing). Server mode (`mode="server"`): the grid does none of that; filters go to the server, sorting and paging are the table's and the pager's server forms (`sort-change`, sorter links, `page-url`).
- **Mirrored attributes.** A table the grid creates takes its look and behaviour from the grid: `label`, `row-key`, `selectable`, `selection-name`, `striped`, `dense`, `bordered`, `sticky-header`, `scroll`, `layout`, `loading`, `loading-rows`, `empty-text`, `empty-label`, `empty-heading`, `empty-message` and the initial `sort`. A table written inside is left alone.
- **Filters in the heading.** The filter row is a second `<thead>` row (`tr.kakao-grid-view-filters`), as in Yii2. The table only reads the first heading row and, with the change below, keeps further rows when it redraws. Each cell holds a field named by `filter-name` (`{key}` replaced), labelled "Filter {label}". `kakao-text-input` (`type="search"`, `size="sm"`, `clearable`) and `kakao-select` (`size="sm"`, an "All" option with value "") where defined, else native `<input type="search">` / `<select>`; a field drawn natively is redrawn when the component is defined later, keeping its value. A server's own filter row (`tr.filters` or `tr[data-filters]` in the `<thead>`) is used as written: its fields are read by name.
- **When a filter applies.** Client mode: text on `input`, debounced by `filter-delay` (300 ms); a dropdown at once. The page goes back to 1. Server mode: text on `change` (Enter or leaving the field), dropdown at once, as Yii's `yii.gridView` does. Both fire a cancelable `filter-change` `{ filters, params, source }` (`filters` by column key, `params` by field name). Not cancelled in server mode, the grid goes to `filter-url` (default: the current address) with the current query, minus the old filter parameters and `page`, plus the non-empty filters. Cancelled, the page loads the rows itself (`rows`, `total-items`, `loading`).
- **Text matching.** Case and accents are ignored; a search matches anywhere in the value as text (raw value, else the cell text); a dropdown matches the value exactly. A column may give `filter.match(value, query, row)`.
- **Action column.** A column with `actions` becomes a table column with `hideLabel`, `type: "actions"` and a `render` that draws the buttons. Built-in names `view`, `update`, `delete` bring a label and an icon (eye, pencil, bin; inline SVG in currentColor); `delete` asks "Delete this item?" and is danger-toned. `url` (or the grid's `action-url`, `{action}` and `{id}`) makes it a link, every `{key}` filled from the row, URL-encoded. The accessible name is "{action} {row}" (the row's first value), so ten "Delete" buttons are told apart. Event actions use `kakao-button` (`variant="ghost"`, `size="sm"`, `icon-position="only"`), links an `<a>` styled to the same size and shape by the grid's own settings; danger actions take the danger colour. In the wrapped form every action shows its label (`icon-position="left"`).
- **Confirm and method.** With yii.js on the page (`window.yii`), `data-confirm` / `data-method` are written and Yii handles them. Without it the grid asks with `window.confirm()` and, for a link with a `method` other than GET, submits a small POST form (with the CSRF parameter from Yii's `csrf-param` / `csrf-token` meta tags). `row-action` fires after the confirmation; cancelled, nothing else happens.
- **Server action cells.** A column whose heading has `data-type="actions"` (or `data-actions`) is an action column in server markup: its links and buttons get the action look and fire `row-action` (`data-action`, else the title) on click.
- **Paging.** `page-size` (20; `0` turns paging off), `page`, `page-sizes`; the grid creates the pager with `total-items`, `page-size` and `summary` off (the grid has its own). Client mode answers `page-change` and `page-size-change`. Server mode passes `total-items`, `page`, `page-size` and `page-url` (as the pager's `url`). Without `kakao-pagination` defined, client mode shows all rows until it is.
- **Summary.** A line above the table, a polite status region: "Showing {from}–{to} of {total}", with "(filtered from {all})" while filters hide rows, "No entries" for none. `hide-summary` drops it. Server mode shows it when `total-items` is known.
- **Selection across pages.** The grid keeps its own set of selected ids; after a page or filter change it gives the table the ids that are on the page. `selected` returns them all.
- **Wrapped form.** The table's tools line is the documented container for a grid's controls: the grid puts a "Filters" disclosure button there (a native button in the look of the "Sort by" select, with the number of active filters). Open, the filter row is shown above the blocks as a column of labelled fields (labels from `data-label` through `::before`); closed it is hidden. The table hides its tools line when there are no rows; the grid shows it again while filters exist, so filters that match nothing can be changed. Each block's action cell is moved to the bottom by flex order, full width, its buttons wrapping. The grid listens to `table-render` and the `data-stacked` attribute to re-place its parts.
- **Changes to the table.** `_build` now reuses the existing `<thead>`: the first row is rebuilt only when the column objects changed, further rows are kept, and only the bodies are replaced. Setting `rows` therefore no longer drops focus from a sort button or a filter field. Nothing else changes for existing users.

## Out of scope

- Inline editing, column hiding / reordering, export, row expansion, grouping, a date-range filter, multi-column sort.
- Upgrading a server's native filter fields to kakao fields.
