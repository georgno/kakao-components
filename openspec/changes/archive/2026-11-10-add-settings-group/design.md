# Design

## Context

Shadow DOM component like card and accordion: styles in the shadow root, defaults in one settings block. Style guide rules that apply: hairlines in 12% text colour (as the accordion's rows; `line` equals `subtle` in some themes), radius lg 14px for the bordered surface and md 10px for rows inside it (nesting rule: 14 − 4 padding), focus `outline: 2px solid var(--kakao-color-focus)` with a 2px offset, hover as a 4.5% ink wash on ghost surfaces, disabled opacity 0.45, standard easing for colour, sentence case, "Naming form fields": a control without a visible label is named by `aria-label`.

## Decisions

- **A second element, `<kakao-setting>`, for rows, defined in the same file.** Rows carry their own options (label, hint, href, action, variant, disabled, layout) and their own shadow DOM; as plain slotted `<div>`s the group would have to parse and restyle children it doesn't own, and page CSS would leak in. Both elements live in `settings-group.js`: one folder per component, one inlineable file. Both shadow roots interpolate one shared settings string, so the file still has exactly one `@kakao-settings` block and the construction server can save it.
- **Group semantics: `role="group"` named by the title, not `<fieldset>`.** A shadow `<fieldset>` brings no `disabled` propagation to slotted controls (that follows the DOM tree, not the flat tree), and its rendering quirks (min-content minimum width, legend placement) fight the layout. A div with `role="group"`, `aria-labelledby` the title and `aria-describedby` the description gives the same announcement. `heading-level` adds `role="heading"` to the title, for settings pages navigated by headings.
- **Naming controls across shadow roots.** The row's label lives in its shadow root, the control in the light DOM, and a library control's focusable part in the control's own shadow root, so ID references (`for`, `aria-labelledby`, `aria-describedby`) can't connect them. The row copies its label as a string instead: `label` on switch group, slider and step switch (their accessible label attribute), `aria-label` on the inner input of a number input, on native controls and on every other control (text input, select, combobox, radio group, button…), following the "Naming form fields" rule. A control the author already named (`label` or `aria-label`) is left alone; the row removes only names it set itself. The hint reaches native controls as `aria-description`; for library controls it is only read in reading order (documented limit). Checkboxes name themselves from their own visible label and are not changed. Clicking the row's label focuses the control.
- **Slider label.** A slider shows its `label` above the track; inside a row that repeats the row's label, so a page-level rule (added once, like the card's glow rules) hides `kakao-setting > kakao-slider::part(label)`. Its numeric field stays.
- **Single switch.** There is no single switch element; a `<kakao-switch-group>` with one item works. With an empty item label, the switch group (small change) uses its own `label` as the switch's name and hides the empty label box, and the row sets that `label`.
- **Hairlines without knowing the position.** The group gives every slotted row but the first a private custom property with the line colour; the row draws its hairline from it (a `::before`, inset by the row padding in the box look). A row outside a group draws none.
- **Looks by context.** Like the accordion's nesting: box (surface, border, 14px radius, 4px padding, rows with 10px rounded hover) at the top; plain (transparent, no border, no side padding so the card's padding is the indent, hairlines full width) when a `kakao-card`, `kakao-accordion`, `kakao-dialog` or `kakao-aside-sheet` is an ancestor (across shadow roots), worked out on connect. `variant` forces.
- **Narrow layout by container query.** The row host is an inline-size container; below 30rem the control drops under the label and wide controls (fields, select, slider) take the full width. Rows whose control is a switch group or checkbox keep it inline, as phone settings do; the row marks them on slotchange. `layout="inline" | "stack"` forces. Breakpoints can't be custom properties, so 30rem is fixed and documented.
- **Link and action rows.** `href` renders the row as an `<a>` (name: label and trailing value; description: hint) with a chevron that mirrors in right-to-left text; `action` renders a `<button>` and sends a bubbling, composed `setting-action` event with `{ label }`. Their default slot holds non-interactive trailing content only (a badge).

## Risks / Trade-offs

- [The hint isn't announced with library controls] → it is read in reading order before the control; documented. Fixing it needs reference targets across shadow roots, which browsers don't ship yet.
- [Look and inline-control marking are computed on connect / slotchange] → moving a group recomputes; changing a control's type is a slotchange anyway.
- [The row writes attributes on its child] → only names, only when the author gave none, and only removes what it set.
