Style guide

How kakao components should look, feel and be themed. Built from a close reading of the first eleven components (later ones join the audit below): what they already agree on is written down as the rule; where they disagree, the guide picks a direction.

Principles

The common character of the best-finished components (button, tabs, switches): quiet surfaces, one confident colour, and controls that feel physical.

01

Quiet by default

Neutral greys carry the layout. Fills are soft (#f0f0f1, #ebebeb), borders are hairlines, shadows are barely there. Nothing competes with content.

02

Ink for actions, accent for state

The main action is near-black ink. The indigo accent marks state: a switch that is on, the filled part of a slider, a selected step. Never both jobs.

03

Tactile motion

Thumbs overshoot a little and settle (spring easing), squash while dragged, and glow while held. Motion explains what changed; it is never decoration, and it stops under reduced motion.

04

Tokens first

Every visual value is a --kakao-<component>-* property whose default points at a main variable with a literal fallback. A page restyles everything by setting a handful of main variables.

05

Accessible without trying

Text meets 4.5:1, UI boundaries and focus indicators meet 3:1, everything works from the keyboard. The defaults must pass on their own.

06

Works anywhere

No dependency, no build step, no required font. A component dropped into a Yii2 page with none of our CSS still looks right.

Typography

Inter Tight is the project font. It is optional for the components: they use it only when the page loads it.

How it is wired Now

The main variable --kakao-font-family is "Inter Tight", system-ui, -apple-system, "Segoe UI", sans-serif. Every component font property defaults to it, with a system font as the literal fallback. shared/font.css loads the font file from Google Fonts.

<!-- project pages: Inter Tight -->
<link rel="stylesheet" href="shared/tokens.css">
<link rel="stylesheet" href="shared/font.css">

<!-- elsewhere: leave font.css out → system font,
     or bring your own -->
:root { --kakao-font-family: "Your Font", sans-serif; }

Why Inter Tight

Inter's tighter-spaced cut. It suits the small, dense labels of controls (11–16px), has a variable weight axis (the button's 550 weight renders exactly), tabular figures for numbers, and true italics (used for “unknown” values in the multi dropdown).

No uppercase Rule

Never style text in capitals: no text-transform: uppercase, no font-variant: small-caps, no wide letter-spacing to fake it. Labels, headings, buttons, tabs, badges and table headers are all written in sentence case. Make a label stand out with weight (600) and colour (muted), not capitals.

Why: capitals are harder to read at the small sizes where they usually show up, they hide word shapes, screen readers sometimes spell them out letter by letter, and they need extra tracking that Inter Tight's tight spacing is designed to avoid. Exception: words that are spelled in capitals anyway (PDF, ZIP, URL, CSV) are written that way in the text itself, not produced by CSS.

Selection is shown with weight as well as colour (tabs 400 → 600, step switch 400 → 700). Keep that pairing so state never depends on colour alone.

Numbers

1,280.00 tabular

Any value that changes in place (slider input, multi dropdown, animated number, counters) uses font-variant-numeric: tabular-nums so the layout doesn't jump. Themes

Light, Beige (a warm mid-tone), Umber (its dark counterpart), dark, AMOLED (true black), Catppuccin (Mocha) and Forest (green-hued dark). The switch toggles light and dark; a <kakao-button theme-picker> menu or a <kakao-step-switch theme-picker> can pick any theme, and both follow the pointer. A theme only changes the colour variables. Components never hard-code a colour, so every theme reaches every component.

Picking a theme with a step switch

A step switch with theme-picker lists the themes as steps, and the page follows the thumb: drag it across the track (or tap further away and watch it fly) and the theme changes with every step it crosses. A <kakao-button theme-picker> menu does the same for the pointer: run down the list and the page changes with each item. Both cross-fade the theme's colour roles instead of rippling, so the control under the pointer keeps rendering. theme-switch.js does the wiring, so a page needs no script for it.

How it works Now

The light values live in shared/tokens.css; every other theme is a block in shared/themes.css. A page picks a theme with data-kakao-theme on <html>, which is what the switch sets. Any element can carry the attribute to theme just that part, as the seven panels above do.

With no choice made, the page follows the system's light/dark setting. data-bs-theme="dark" also selects dark, and the switch keeps it in step, so a Bootstrap 5.3 page and the components always agree.

Accessibility rules Rule

  • Every theme passes node tools/check-themes.js: text 4.5:1; control borders, filled controls and focus 3:1.
  • The system's increase contrast setting strengthens muted text, borders and hairlines in every theme.
  • With reduce motion the theme changes at once: no ripple.
  • The default follows the system, and a choice is remembered.
  • Each theme sets color-scheme, so native controls and scrollbars match.

Adding a theme

  1. In shared/themes.css, copy the dark block, rename it (/* @theme dim */, [data-kakao-theme="dim"]) and set its color-scheme.
  2. Run node tools/check-themes.js --fix and adjust colours until it passes.
  3. Add it to the switch: list-data='[{"value":"light"},{"value":"dark"},{"value":"dim","scheme":"dark"}]'. The switch then cycles through all three, and any <kakao-step-switch theme-picker> or theme menu can list it too.

Control heights Proposed

The button already defines 36 / 44 / 52px. Text fields, dropdowns and the number input should use the same heights so a button and a field line up in a form row. Today the multi dropdown and number input size themselves from padding and line height, and come out shorter than 44px.

Toggles are their own family: tracks are 28px (1.75rem) tall with a 22px thumb and 3px inset. Keep the tap target at least 24×24px (WCAG 2.5.8).

Shape

Corners are generous and rounder as things get bigger. Radii in use today: 3, 4, 6, 7, 8, 9, 10, 11, 13, 14, 15 and 999px. They reduce to five steps.

Radius scale Proposed

The examples are drawn at the proposed radius. Live components keep their current radii until the scale is decided. Corners set by the nesting rule (a dialog corner holding a button: 33px for md) sit outside the scale on purpose. Buttons keep their own size-linked radii (11 / 13 / 15px). It's a deliberate “squircle-ish” ratio of about 0.3 × height. The list (4px), popover (4px) and slider input (3px) are the outliers and read as a different library next to them.

Nesting rule Now

Inner radius = outer radius − padding. Tabs (10 − 4 = 6) and the button segment (14 − 4 = 10) already do this. It's why their thumbs look concentric. Apply it to every container with a rounded child: menus and their options, drop zone and file rows. Read the other way, outer = inner + padding: a dialog corner that holds a filled footer button is that button's radius plus the dialog padding (md: 13 + 20 = 33px), so the two curves sit concentric. The dialog measures which corners hold a button; a ghost button has no visible shape at rest (only a faint wash on hover) and doesn't count. Its other corners have no rounded child and stay at 14px. The card keeps 14px on purpose: the corner fitting is dialog-only.

Elevation

Shadows are soft and wide, never dark. Today there are six different shadow recipes plus “none” for the popover. They reduce to three levels.

1 · RestingTab thumb, pressed segment, primary button glow.
0 2px 24px rgb(0 0 0/.04)
2 · RaisedDraggable thumbs (switches, slider).
0 1px 3px rgb(0 0 0/.18),
0 1px 8px rgb(0 0 0/.06)
3 · OverlayPopover, dropdown panel, menus.
0 8px 24px rgb(0 0 0/.08),
0 0 0 1px rgb(0 0 0/.05)

The 1px ring in levels 1 and 3 replaces a separate border, so overlays stay crisp on any background. Exception: toasts use level 3 without the ring, because they hold alerts, and alerts have no edge. In light themes they make up for the missing edge with a contact shadow under the soft one (0 1px 3px rgb(0 0 0/.14), 0 8px 24px rgb(0 0 0/.16)), a fill from the raised colour and a 16% tint (alerts too); dark themes keep plain level 3 and 10%. The switch thumb's current 0 1px 3px rgba(0,0,0,.3) is the heaviest shadow in the set; level 2 softens it.

Focus & states

Two focus styles ship today: a soft translucent halo (button, number input, multi dropdown) and a solid 2px outline (switches, slider, list, popover, tabs). The halo looks nicer but fails the 3:1 rule.

Focus indicator Proposed

Disabled Proposed

Disabled opacity ranges from 0.2 to 0.55 across components. Use one value: 0.45. At 0.2 (button, tabs) a disabled label is close to unreadable, and people still need to read what's unavailable.

Interaction states Now

Hover darkens a fill one step (ink → #2c2c31, secondary #f0f0f1 → #e6e6e8) or adds a 4.5% ink wash on ghost surfaces.

Pressed / held scales slightly and glows (tabs hold glow, button press).

Busy swaps the label for a spinner and keeps the width; success shows a brief tick (button, switch).

Error uses danger on the track or border plus a text message. Never colour alone.

Easing Rule

Spring (--kakao-ease-spring) for things that move into place along a line: a switch thumb, a chip sliding along its row. Standard (--kakao-ease-standard) for everything else: fades, colour, size, and any move that crosses a line break, because a spring would swing across the break. One exception: a thumb's squash and stretch belongs to its move and rides the spring with it. Both curves are main variables in tokens.css; every setting that uses one of them defaults to the token.

Other curves still in use in component and shared JS/CSS, to review against the two above: cubic-bezier(.4, 0, .2, 1) (5×), (.22, 1, .36, 1) (4×), (.34, 1.3, .64, 1) (6×), (.34, 1.56, .64, 1) (3×), (.25, 1, .5, 1) (3×) and (.2, .8, .3, 1) (1×).

Reduced motion: components honour prefers-reduced-motion, except Missing list (smooth scroll, fade), slider (thumb glide) and number input.

Trigger API

Components don't know each other, so they talk through one small layer: shared/component-api.js. A trigger is a custom event named kakao-trigger:<name> that bubbles and crosses shadow roots; a reaction is a component listening for one. Load the file before the components; they check for KakaoComponents and keep working without it.

Emitting and reacting

/* a component announces something */
KakaoComponents.emit(this, 'theme-change', {
  color: '#818cf8'   // plus source, trigger
});

/* another one reacts */
const off = KakaoComponents.on('theme-change', (d) => {
  glow.style.setProperty('--glow', d.color);
});
off(); /* unsubscribe */

Discovery

Every component declares what it emits and what it watches, so the wiring is documented where it lives.

KakaoComponents.register('kakao-card', {
  triggers: [],
  reactions: { 'theme-change': 'glow color' },
});

KakaoComponents.meta('kakao-card');

Live wiring: <kakao-theme-switch> emits theme-change with the new theme's primary colour. <kakao-card> reacts with it: a card without a footer button glows in that colour after a theme change. Its theme-change event carries the same color, so plain page listeners get it too.

Component rules

Decisions that belong to one component family rather than to the whole system.

Status tones Rule

Badges and chips share one recipe for their soft tones (primary, success, danger): the fill is 16% of the tone colour in the surface, the text is 72% of the tone colour in the theme's text colour. It passes 4.5:1 in all seven themes (lowest: 4.74:1, danger in umber). Neutral uses the subtle-strong fill, ink the solid ink.

Outline badge Rule

An outline badge means something is missing or only informational: "Missing", "Draft 0.1". It has no fill and muted text, so it never competes with a status.

Missing

Dialog footer Rule

button-position puts the footer buttons left, center or right (default); full-width splits the whole width equally between them. With more than one button, the main (filled) button always sits in the corner: last when they sit right (the default) or fill the width, first when they sit left; centred buttons have no corner, so it comes last. A bottom corner rounds to button radius + padding only when a filled button sits in it; ghost buttons and button-free corners keep the dialog radius. The dialog is the only component that forces its own spacing on slotted content (header, body, footer margins are reset over page styles); the card doesn't.

Button order Rule

Dialogs: the main button sits in the corner (last on the right, first on the left; see Dialog footer). Cards: main button first in the footer, which is also what gives the card its glow.

Naming form fields Rule

A form component with no visible label takes its accessible name from aria-label on the element (text input, textarea, radio group, colour picker). Use it whenever the label sits beside the field, as in the kitchen sink.

Edge fade on horizontal scrollers Rule

Overflowing horizontal scrollers get an edge fade. A row that scrolls sideways (the header bar's links, tabs, a step switch or switch group too wide for its space) fades out at each edge where there is more to scroll, and only there: no fade at an end it has reached, none at all when everything fits. The fade is a mask, so it works on any background and theme; its width is the main variable --kakao-scroll-fade.

Fixed hosts reset their margin Rule

A component whose host is fixed to the viewport resets its own margin (margin: 0 !important on :host), so page spacing rules (e.g. sibling margins in a card) can't shift it. Normal page declarations beat :host, so only !important holds. Followed by dialog, aside sheet and toast.

Suggested order

  1. Accessibility first: focus outline everywhere, plus the contrast fixes in the table above. Small changes with a big effect.
  2. Neutrals: Done colour roles and themes; every component's colours follow them.
  3. Shape & elevation: radius and shadow tokens; restyle list, popover and slider.
  4. Sizes: align fields to the 36/44/52 control heights.
  5. Type scale: swap hard-coded px font sizes for the scale tokens.

Each step fits an OpenSpec change and gets its construction pages updated. The existing settings blocks make every step a change to defaults, not to markup.
